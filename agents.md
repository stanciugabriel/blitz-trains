# Agent Notes

## Project Vision
- Build "Raily" – a glassmorphic, Flighty-style native iOS app tracking CFR Călători trains.
- Fuse offline GTFS schedule data with live OCR (StationBoardScanner) for platform/delay truth.
- Keep MapKit visible at all times, layering glass cards and sheets for content.

## Key Components
1. **Trip / TripStore**: merges offline GTFS data, live OCR platform/delay, seat + booking state, and coordinate polylines.
2. **MainDashboardView**: map background with straight geodesic overlays, floating "My Trips" glass sheet, Flighty-style list, add-trip modal, and empty-state arrow.
3. **TripDetailView**: detail screen with map showing every station pin + curved path, vertical timeline (TimelineRowView), metadata grid (platform hero, seat + booking editables), and "Where is my train?" progress banner.
4. **Add Trip Modal**: Flighty-like picker w/ train-number search, Yesterday/Today/Tomorrow/Pick Date pills, and GTFS results list.

## Visual + UX Requirements
- Full-screen MapKit background.
- Glass Flighty aesthetic: `.ultraThinMaterial` / `.systemMaterialDark`, SF Pro Rounded, white text plus safety orange / signal green accents.
- Dashboard sheet anchored to lower 40% with "My Trips" header, + button, empty-state arrow, and operator/date/route layout.
- Detail sheet: vertical timeline at top, metadata grid in middle, platform tile emphasized, "Where is my train?" progress + copy at bottom.

## Latest Search and Automatic Trip Detection Work
- Train search no longer performs the expensive SQLite query on the UI path. `GTFSDataSource` uses a dedicated read-only search connection serialized through its own queue, while the normal GTFS connection remains separate. The data source is explicitly nonisolated so background calls do not implicitly hop back to the MainActor.
- Search SQL filters matching train numbers before resolving first/last route segments, uses prefix matching for numeric train-number input, and deduplicates repeated route rows because `Trip.id` is currently the train number. Station-name matching remains supported.
- The add-trip search field uses a dedicated local SwiftUI child (`TrainNumberSearchInput`) so each keystroke does not update the root dashboard/map state. Because Apple's `numberPad` has no native Return key, it uses the Apple `numbersAndPunctuation` keyboard with a native Search action and filters the value to digits. There is no minimum character requirement, no debounce, and no custom floating keyboard button. Typing alone must not start a query.
- Search results have explicit loading state (`Searching schedules…`) and only show “No trains found” after a completed query. Request IDs and query checks prevent stale results from replacing newer input. Empty/one-character input clears results without querying. Search result train IDs are unique to avoid SwiftUI duplicate-ID warnings.
- The earlier UIKit-backed replacement for the search field was reverted because it broke intrinsic sizing and focus. Keep the local SwiftUI child approach unless a replacement preserves keyboard focus and layout.
- Added a persisted Settings toggle, `TripLocationDetectionPreferences.isEnabled`, for “Automatic boarding and arrival detection.” The preference is stored in `UserDefaults` under `raily.automaticStationDetection`, survives launches, and broadcasts changes immediately.
- `TripLocationPhaseDetector` implements fast confidence-based phases: `unknown`, `atOrigin`, `boarded`, and `arrived`. It is driven by regular active location updates and route progress; it does not currently register OS-level `CLCircularRegion` monitors.
- Automatic detection rules currently are:
  - Ignore fixes with invalid horizontal accuracy or accuracy worse than 150 m.
  - Origin and destination station proximity radii are `max(250 m, horizontalAccuracy × 1.5)`.
  - Entering the origin radius changes `unknown` to `atOrigin` immediately.
  - Boarding requires route proximity within `max(500 m, horizontalAccuracy × 3)`, route progress at least 250 m beyond the origin projection, and movement evidence: GPS speed at least 1 m/s, or more than 100 m physical movement / 150 m route progress since the previous fix. There is intentionally no dwell timer.
  - Arrival requires the `boarded` phase, route proximity, being within the destination radius, and route progress no more than 350 m before the destination projection. There is intentionally no dwell timer.
  - Once `arrived`, the phase remains confirmed for that trip instance and location tracking can stop. A single bad fix cannot reverse it.
- When automatic detection is enabled, timetable arrival no longer forces the map to jump to the terminal marker. Before boarding, the train marker remains active; after the scheduled service arrival, an unconfirmed trip continues showing the device location when available. After confirmed boarding, the user location is preferred until confirmed arrival.
- The detector projects GPS coordinates onto the saved InfoFer route polyline, falling back to static polyline stops when needed. Its projection uses local latitude/longitude vector math and route-distance progress, not just straight-line station distance.
- The current implementation depends on normal foreground/active-trip location updates. Future work should add explicit state persistence/cleanup per trip travel date, optional manual overrides, and background location authorization/region monitoring if automatic detection must continue while the app is suspended.
- Add-trip UI cleanup: Pick Date uses a dedicated compact layout rather than inheriting the Search screen's input/random-trip spacing, and the graphical date picker hides its unused label slot. Do not add animated step transitions; Search, Pick Date, Origin, and Destination should change immediately. The home screen should not render the old static “Search to add trains” button because Search is already available in the navigation bar and the intermediary add-trip screen.
- Automatic trip detection must account for Romanian Regio/Regio Express services yielding to IR/IC trains. A long stop at any station is normal train operation, not an early exit. Model intermediate stops as `holdingAtStation` only when the observed stop exceeds that station's scheduled stop duration plus a configurable grace period; never show a holding warning for a normal scheduled stop.
- Use all route stations as logical GPS/delay checkpoints, but only the selected destination can automatically complete the user's trip. Stations not in the selected itinerary may help explain delay/route progress but must not change the user's boarding or arrival state.
- Early-exit detection must be conservative. A possible early exit requires evidence that the user has left both the station area and railway route, route progress has stopped or diverged, and the divergence is not explained by a GPS gap or a train waiting to resume. Prefer a non-destructive suggestion such as “Continue tracking to …” or “Did you get off at …?” over automatic trip completion.
- GPS and mobile data are independent signals. During mobile-data gaps, preserve valid local GPS samples with timestamps, horizontal accuracy, speed, route progress, and the last known phase. Do not require InfoFer for local phase tracking. When connectivity returns, reconcile local checkpoints with the latest InfoFer station checkpoint and reject stale, out-of-order, or physically impossible jumps.
- Delay prediction should fuse InfoFer station checkpoints with GPS-derived route progress. InfoFer remains the authoritative confirmed checkpoint; GPS interpolates an estimated delay between checkpoints. Label the source explicitly (`InfoFer confirmed`, `GPS estimated`, or `awaiting next station update`) and never present a GPS estimate as exact intermediary delay.
- A train waiting for traffic should only be described as holding when its observed stop exceeds the scheduled stop duration plus grace. While the stop is within the normal window, show no holding message. After the threshold, show a neutral explanation such as “Extended stop — timing may update when the train departs,” and clear it as soon as forward route progress resumes.
- The app must support users who do not keep it open. On launch or foreground, reconcile the saved trip state from current GPS, persisted checkpoints, schedule, station delays, and InfoFer. Dynamic Island rendering is not a substitute for location processing. Continuous background GPS requires explicit background location configuration and permission; otherwise rely on best-effort region/significant-change wakeups, InfoFer/server updates, and foreground reconciliation.
- Live Activity updates can be driven remotely through APNs only after a backend and push-token flow exist. Do not assume Live Activity timers execute arbitrary tracking logic while the app is suspended. Preserve last confirmed state when no new evidence is available.
- Trips added more than one hour before adjusted departure should not start a Live Activity immediately. `LiveActivityManager` schedules a `BGAppRefreshTask` for the one-hour window, starts eligible saved trips when iOS wakes the app, and reschedules the next pending trip. Foreground reconciliation remains a fallback; guaranteed starts after force-quit require ActivityKit push-to-start plus a server.
- Settings now provides versioned JSON `Export Trips`, schema-validated `Import Trips`, and explicit `Delete All Data` actions. Import merges by trip identity plus travel date without overwriting existing records. Delete-all clears active/past trips, profile data, tracking evidence, delay/forecast state, preferences, and Live Activities while retaining bundled read-only schedules.
- The automatic detector's durable state is keyed by trip instance and travel date. It persists phase and the last reliable GPS sample (timestamp, coordinate, and route progress), removes state when a trip is deleted, and prunes state older than two days on launch.
- Automatic detection requests Always location authorization when the user enables tracking. The app target declares both location usage descriptions and the `location` background mode. Normal mode uses roughly 50 m updates and allows background updates; the persisted “Save battery” setting uses kilometer accuracy, a 250 m distance filter, automatic pausing, and significant-change monitoring instead of continuous background GPS.
- Intermediate itinerary stations are checked as traffic/holding checkpoints. A station is marked as holding only when the device is within the station radius and the observed timestamp is more than 3 minutes after the scheduled departure.
