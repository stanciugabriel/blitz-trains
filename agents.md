# Agent Notes

## Swiss timetable migration (`sbb` branch)
- Share Extension uses a programmatic `UIViewController` via `NSExtensionPrincipalClass`, not the social-post composer/storyboard. Render loading immediately, show all legs in a scrolling preview, and expose error/retry/saved states. Item-provider reads time out after five seconds and the complete resolution after thirty; cancelled or superseded work must not overwrite the current screen. Accept URL, text and attributed-content links while ignoring preview images for journey extraction.
- `Shared/SBBSharedJourneyResolver.swift` resolves SBB Mobile short links by reading the `www.sbb.ch/.../trip?tripId=` browser handoff in the landing HTML. The observed `3HA` token contains base64url/zlib data with a protobuf-wrapped HAFAS reconstruction. Parse every transit leg; reject unknown/corrupt formats rather than importing a partial journey. This is undocumented snapshot data, not a live-delay source. The extension prefers URL/text attachments over the incomplete share image; no clipboard inspection is used.
- Share Extension “Add to Trips” writes a decoded journey into the `group.ro.openlabs.blitz` App Group inbox as an atomic JSON file. Both targets require this entitlement in their provisioning profiles. On launch/foreground, SBB's shared legs are authoritative: persist each original leg in `Trip.sharedJourneyLeg`, and prefer its absolute terminal times in `TripTimingResolver`. Exact GTFS matches enrich the trip with route/operator/platform data, but missing services, calendar differences and changed times must not block importing. Unmatched legs keep only known terminal coordinates from the share (or static station lookup), with no invented intermediate timetable or GTFS trip ID. Preserve `sharedJourneyLeg` in every Trip copy/edit helper. Persist all legs before acknowledging the inbox file; malformed journeys stay pending for retry. Stable imported IDs prevent repeat-share duplicates. Completed legs go to Log; active/future legs go to My Trips and receive normal Live Activity and tracking handling. The extension cannot assume it can launch the containing app: tell the user to open Blitz after saving.
- The active bundled schedule is `blitz/mini_feed.sqlite`, read directly through `GTFSDataSource`. `sbb_gtfs.db` remains on disk but is excluded from app target resources.
- This feed has `agency`, `routes`, `trips`, `stops`, `stop_times`, `transfers`, and `shapes`. It includes `calendar` and lossless `calendar_date_masks` (raw or zlib-compressed, two bits per day), but no delay history. Search filters candidates using weekly service and packed date exceptions. Automatic alternative recommendations remain unimplemented. Do not infer daily operation from `service_id` strings.
- `Trip.gtfsTripId` is the opaque GTFS `trip_id`; it is not a train number. Search IDs are prefixed with `sbb:` and `trip_short_name` supplies the display number. Always use `gtfsTripId` for data-source lookups.
- Search groups by operator, line, and final station, regardless of train number. Each group retains all matching services; the original numeric/line query stays applied after selection. Station choices union candidate routes and final rows show the selected leg, deduplicated by train and terminal times. `calendar`, `calendar_dates`, and `calendar_date_masks` support date filtering with exceptions and overnight boarding. Packed masks override weekly service only for add/remove values; zero and absent masks fall back to the weekly calendar. Decode using zlib for codec 1 and calendar-day offsets in Europe/Zurich.
- Add-trip calendar loads month availability off the main thread for the selected suggestion and original search query. Green dots mark valid boarding dates, unavailable days are disabled, and Continue requires an available selection. Use calendar-day offsets and include boarding after midnight on prior-day services.
- Stops use parent-station identity where available, with platform codes read from the trip's actual child stop. `mini_feed` retains those parent IDs but omits the parent rows. Numeric stop sequences preserve zero-dwell commercial stops; adjacent stop times form segments. Dashboard/detail route lines use the feed's shapes, loaded asynchronously and clipped by stop sequence and shape distance. `GTFSRouteGeometry` aligns small distance discrepancies introduced by shape simplification. Missing/invalid shapes fall back to station-to-station lines. Tracking and train-marker interpolation still use their existing station-based behavior. Speed/length/tonnage and historical delay values are unavailable.
- Timetable date math and clock formatting use Europe/Zurich. Active/past Swiss trips use `sbb.savedTrips` / `sbb.pastTrips`, preserving Romanian saved data separately.
- `SBBDataSourceTests.swift` covers fixture mapping, shared train numbers, numeric sequence ordering, platforms, overnight times, missing metadata, and real bundled Swiss service lookup.
- The old Romanian network scraper, webcam board, operator branding, and bundled logos have been removed. Swiss trains use timetable interpolation and rider GPS. Saved GTFS trips receive foreground live delays from the local `sbb-rt` proxy through `GET /trips/:trip_id`, polled each minute near travel time and refreshed on opening an active trip. Never bundle or gate requests using the backend's debug `trips.json` snapshot. A 404 is retried on the next poll. Live delays match the selected service date and stop sequence, support seconds or absolute event timestamps, and update open detail/row views. Stale feeds are ignored. This integration only consumes delays; ActivityKit remote pushes are not implemented.
- Historical notes below describe the Romanian implementation and are superseded by this section on `sbb`.

## Project Vision
- Build "Blitz" – a glassmorphic, Flighty-style native iOS app tracking Swiss rail journeys.
- Use the bundled Swiss GTFS schedule for timetable and platform information.
- Keep MapKit visible at all times, layering glass cards and sheets for content.

## Key Components
1. **Trip / TripStore**: stores Swiss timetable data, seat and booking state, and station coordinates.
2. **MainDashboardView**: map background with straight geodesic overlays, floating "My Trips" glass sheet, Flighty-style list, add-trip modal, and empty-state arrow.
3. **TripDetailView**: detail screen with map showing every station pin + curved path, vertical timeline (TimelineRowView), metadata grid (platform hero, seat + booking editables), and "Where is my train?" progress banner.
4. **Add Trip Modal**: Flighty-like picker w/ train-number search, Yesterday/Today/Tomorrow/Pick Date pills, and GTFS results list.

## Visual + UX Requirements
- Full-screen MapKit background.
- Glass Flighty aesthetic: `.ultraThinMaterial` / `.systemMaterialDark`, SF Pro Rounded, white text plus safety orange / signal green accents.
- Dashboard sheet anchored to lower 40% with "My Trips" header, + button, empty-state arrow, and operator/date/route layout.
- Detail sheet: vertical timeline at top, metadata grid in middle, platform tile emphasized, "Where is my train?" progress + copy at bottom.

## Latest Search and Automatic Trip Detection Work
- Train search no longer performs the expensive SQLite query on the UI path. `GTFSDataSource` uses a dedicated read-only search connection serialized through its own queue, while the normal GTFS connection remains separate. The data source is explicitly nonisolated so background calls do not implicitly hop back to the MainActor.
- Search SQL filters matching train numbers before resolving first/last route segments, uses prefix matching for numeric train-number input, and deduplicates repeated route rows because `Trip.id` is currently the train number. Station-name matching remains supported.
- The add-trip search field uses a dedicated local SwiftUI child (`TrainNumberSearchInput`) so each keystroke does not update the root dashboard/map state. Because Apple's `numberPad` has no native Return key, it uses the Apple `numbersAndPunctuation` keyboard with a native Search action and filters the value to digits. There is no minimum character requirement, no debounce, and no custom floating keyboard button. Typing alone must not start a query.
- Search results have explicit loading state (`Searching schedules…`) and only show “No trains found” after a completed query. Request IDs and query checks prevent stale results from replacing newer input. Empty/one-character input clears results without querying. Search result train IDs are unique to avoid SwiftUI duplicate-ID warnings.
- The earlier UIKit-backed replacement for the search field was reverted because it broke intrinsic sizing and focus. Keep the local SwiftUI child approach unless a replacement preserves keyboard focus and layout.
- Added a persisted Settings toggle, `TripLocationDetectionPreferences.isEnabled`, for “Automatic boarding and arrival detection.” The preference is stored in `UserDefaults` under `raily.automaticStationDetection`, survives launches, and broadcasts changes immediately.
- `TripLocationPhaseDetector` implements fast confidence-based phases: `unknown`, `atOrigin`, `boarded`, and `arrived`. It is driven by regular active location updates and route progress; it does not currently register OS-level `CLCircularRegion` monitors.
- Automatic detection rules currently are:
  - Ignore fixes with invalid horizontal accuracy or accuracy worse than 150 m.
  - Origin and destination station proximity radii are `max(250 m, horizontalAccuracy × 1.5)`.
  - Entering the origin radius changes `unknown` to `atOrigin` immediately.
  - Boarding requires route proximity within `max(500 m, horizontalAccuracy × 3)`, route progress at least 250 m beyond the origin projection, and movement evidence: GPS speed at least 1 m/s, or more than 100 m physical movement / 150 m route progress since the previous fix. There is intentionally no dwell timer.
  - Arrival requires the `boarded` phase, route proximity, being within the destination radius, and route progress no more than 350 m before the destination projection. There is intentionally no dwell timer.
  - Once `arrived`, the phase remains confirmed for that trip instance and location tracking can stop. A single bad fix cannot reverse it.
- When automatic detection is enabled, timetable arrival no longer forces the map to jump to the terminal marker. Before boarding, the train marker remains active; after the scheduled service arrival, an unconfirmed trip continues showing the device location when available. After confirmed boarding, the user location is preferred until confirmed arrival.
- The current implementation depends on normal foreground/active-trip location updates. Future work should add explicit state persistence/cleanup per trip travel date, optional manual overrides, and background location authorization/region monitoring if automatic detection must continue while the app is suspended.
- Add-trip UI cleanup: Pick Date uses a dedicated compact layout rather than inheriting the Search screen's input/random-trip spacing, and the graphical date picker hides its unused label slot. Do not add animated step transitions; Search, Pick Date, Origin, and Destination should change immediately. The home screen should not render the old static “Search to add trains” button because Search is already available in the navigation bar and the intermediary add-trip screen.
- Use all route stations as logical GPS/delay checkpoints, but only the selected destination can automatically complete the user's trip. Stations not in the selected itinerary may help explain delay/route progress but must not change the user's boarding or arrival state.
- A train waiting for traffic should only be described as holding when its observed stop exceeds the scheduled stop duration plus grace. While the stop is within the normal window, show no holding message. After the threshold, show a neutral explanation such as “Extended stop — timing may update when the train departs,” and clear it as soon as forward route progress resumes.
- Live Activity updates can be driven remotely through APNs only after a backend and push-token flow exist. Do not assume Live Activity timers execute arbitrary tracking logic while the app is suspended. Preserve last confirmed state when no new evidence is available.
- Trips added more than one hour before adjusted departure should not start a Live Activity immediately. `LiveActivityManager` schedules a `BGAppRefreshTask` for the one-hour window, starts eligible saved trips when iOS wakes the app, and reschedules the next pending trip. Foreground reconciliation remains a fallback; guaranteed starts after force-quit require ActivityKit push-to-start plus a server.
- Settings now provides versioned JSON `Export Trips`, schema-validated `Import Trips`, and explicit `Delete All Data` actions. Import merges by trip identity plus travel date without overwriting existing records. Delete-all clears active/past trips, profile data, tracking evidence, delay/forecast state, preferences, and Live Activities while retaining bundled read-only schedules.
- The automatic detector's durable state is keyed by trip instance and travel date. It persists phase and the last reliable GPS sample (timestamp, coordinate, and route progress), removes state when a trip is deleted, and prunes state older than two days on launch.
- Automatic detection requests Always location authorization when the user enables tracking. The app target declares both location usage descriptions and the `location` background mode. Normal mode uses roughly 50 m updates and allows background updates; the persisted “Save battery” setting uses kilometer accuracy, a 250 m distance filter, automatic pausing, and significant-change monitoring instead of continuous background GPS.
- Intermediate itinerary stations are checked as traffic/holding checkpoints. A station is marked as holding only when the device is within the station radius and the observed timestamp is more than 3 minutes after the scheduled departure. Normal scheduled stops never produce a holding message, and the state clears when route progress resumes. Only the selected destination can set the user phase to `arrived`.
- The last reliable CLLocation is persisted locally and restored on launch/foreground. Samples older than 15 minutes are not used to make a new phase decision, preventing a stale location from creating false boarding/arrival state after a long gap.
- High-confidence arrival detection is enabled by default behind the persisted `High-confidence arrival detection` setting. When enabled, destination arrival requires two separate reliable destination fixes at least 10 seconds apart, in addition to route proximity and destination progress. Disabling the setting restores the immediate single-fix behavior for testing.
- An experimental persisted setting exists for missed-train suggestions. It must remain opt-in and must not make automatic trip changes. Missed-train recovery should first confirm that the user reached the origin too late, then offer viable same-station alternatives without replacing the current trip automatically. Train Wi-Fi detection was removed because iOS cannot scan nearby access points and connected-network detection would be unreliable on these trains.
- Missed-train suggestions now require a fresh device GPS fix and an adjusted departure that has passed, but do not require the rider to have reached the origin station. A rider still en route to the station can receive the confirmation prompt; choosing alternatives opens the add/search flow while preserving the original trip.
- Missed-train recovery now presents bundled same-station departures in a confirmation sheet. Alternatives are filtered to future departures, exclude the missed train, retain the original trip until the user selects one, and are labeled as schedule-only when live delay data is unavailable.
- Foreground/on-appear reconciliation explicitly restarts location tracking for the selected trip before evaluating persisted GPS state, because SwiftUI task identity may not change after suspension or relaunch.
- `TripRowView` now uses `TripTimingResolver` for scheduled/adjusted terminal times, station-level versus header delay precedence, overnight normalization, and live delay refreshes. Keep row presentation-only; add shared timing behavior to the resolver and tests.

## Work completed since the SBB migration (2026-09-25)

Since the SBB migration, Blitz has moved from the Romanian static-data assumptions to Swiss GTFS data and now has an end-to-end, backend-backed train-formation experience, with the schedule and rendering work documented below.

- **Swiss data and agency support:** `blitz/sbb_gtfs.db` is the active Swiss schedule source. `GTFSDataSource` reads GTFS `agency`, `routes`, `trips`, `stops`, `stop_times`, `transfers`, and calendar tables, including compact `calendar_date_masks`, while preserving service-date/overnight handling. Swiss operator IDs and logo mappings cover SBB, BLS, Thurbo, TPC, Jungfrau, SZU, RhB, Travys, Aargau Verkehr, and SOB.
- **Search and trip selection:** Search accepts letters, numeric train numbers, service names, and combined inputs such as `IC12 4320`. Repeated GTFS route rows are deduplicated, matching services with the same train name/headsign are merged into one suggestion, and date plus departure/arrival station selection filters the remaining trips before the normal trip-row picker is shown. Calendar availability is derived from the Swiss service exceptions.
- **SBB link importing:** The share-extension flow accepts SBB Mobile links, presents a Blitz-styled import sheet, resolves the shared page data, and sends the imported trip to the main app. The in-app clipboard-paste prompt/button was removed after the share flow became the supported entry point.
- **Formation placement and API decoding:** The formation card is rendered below “My History on This Route” in `TripDetailSheet` and is omitted when no formation is available. The decoder handles scheduled-stop formations, formation-short strings, vehicle identifiers, EVNs, locked vehicles, platform sectors, and the official positional/numbered pictogram syntax. Attributes such as wheelchair, bicycle, stroller, low-floor, family, restaurant, luggage, sleeping, couchette, and business are inferred from the API tokens for every train rather than hard-coded train numbers.
- **Formation vehicle rules:** The EVN model field identifies electric locomotives, EMUs, single-deck cars, and double-deck cars. Lowercase `t` outside parentheses in `typeCodeName` selects the control-car variant; EVN control-car classes are the fallback when the type code is absent. Control cars at consist ends face outward; interior adjacent control cars meet nose to nose; remaining EMU cabs face out of their EVN unit. Default artwork faces left and may be mirrored. Specific `model-left`/`model-right` artwork uses the matching variant without mirroring; `model-f` is left-facing and may be mirrored; unsuffixed specific artwork (including `re460`) is used as supplied in either direction. Artwork is bottom-aligned and scaled uniformly from its exported pixel width.
- **Formation UI:** `TrainFormationPreview` shows car and locomotive artwork, operator/type/EVN metadata, class and amenity badges, seat/bike/wheelchair counts, locked-state styling, and tap hints. Count badges expand horizontally when needed. Platform sectors appear as variable-length blue blocks below the EVN.
- **Formation assets:** Use `el-default`, `c-default`, `cc-default`, `dd-default`, and `ddcc-default` according to the EVN model, with `re460` taking priority for that specific locomotive. EMU control cars use `emuc-default` when that asset is supplied and `cc-default` until then. Generic and `-f` artwork may be mirrored; Re460 retains its lettering orientation.
- **FLIRT artwork:** EVN models 521, 522, 523, 524, 526, and 528 use `flirt-c-f` for normal cars and `flirt-cc-f` for control cars, and show `RABe <model>` instead of the raw type code. These assets face left and may be mirrored using the consist orientation rules. A model-specific asset still takes priority. The formation operator label comes from `Trip.agencyId` via the bundled GTFS `agency` table; do not hard-code SBB or assume EVU 11 when the trip has no agency ID.
- **Formation labels and counts:** Agency ID `11` displays as the short label `SBB`; other formation operators use their GTFS agency name. Bike and wheelchair counts share the icon badge, so a separate duplicate pictogram is omitted when a numeric count exists. Train 25145's cars 1, 6, and 7 have 28 first-class and 16 second-class seats; those are not bike or wheelchair counts.
- **Current formation and Live Activity timing:** First- and second-class seats now share one seat badge (`1:<count> 2:<count>`) with a combined hint; the EVN uses the same 13-point size as the vehicle type. Saved Swiss `Trip.travelDate` is the selected GTFS service date, so `TripTimingResolver` must anchor to it rather than choose a nearby daily run. Live Activities start no earlier than one hour before the resolved departure, whether automatic or manual; missing terminal times and completed trips do not start. The open app checks each minute, and a background refresh is requested for the next window (iOS schedules it best-effort). A user who taps Stop Live suppresses automatic restarts for that trip and service date; tapping Live again clears the suppression.
- **Static schedule persistence:** Added `TripStaticScheduleStore` and `StoredSegment` persistence in `TripStorage.swift`. Once a trip's immutable GTFS segments are resolved, they are saved in `UserDefaults` and reused across launches, so opening saved trips no longer interrogates the bundled SQLite database every time. Newly added GTFS trips capture their segments in a detached utility task.
- **Startup and detail performance:** Stored trip stops are used before falling back to SQLite. GTFS datasource initialization is deferred in the main sheet, detail timing/segment/weather work is loaded concurrently, route data is prewarmed asynchronously, and high-frequency map/detail redraws reuse cached schedule geometry. `DeviceLocationProvider` no longer calls the potentially blocking location-services query from the main-thread tracking path.
- **Formation/API investigation:** The official `train-formation-view` example was inspected and its `formationShortString` conventions were reproduced in the app parser. This fixed missing wheelchair/bike/stroller pictograms and the earlier cases where trains such as 648 and 17365 rendered only class/AC symbols.
- **Validation status:** Swift source errors introduced during the formation work were fixed. The latest source-only `build-for-testing` passed with asset catalogs excluded; the local full build remains blocked by CoreSimulator/actool availability. See the current reference above for focused tests and the remaining simulator check.

- GPS tracking is now explicitly restarted when a selected active trip changes or the add-trip flow closes, preventing the detector from missing an entire journey because it was evaluated before the location provider resumed. Past-trip detail remains excluded from active tracking and missed-train evaluation.
